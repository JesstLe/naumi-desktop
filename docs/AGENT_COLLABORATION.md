# 协作与交接说明

仓库级规则以 [AGENTS.md](../AGENTS.md) 为准。本文件说明在本项目中的执行与记录方式，不替代模块实现文档。

## 开工与文件归属

1. 阅读本文件、仓库规则和相关 `docs/implementation/` 文档；跨模块变更逐一确认职责与依赖。
2. 检查当前分支、工作树、已有 worktree 与任务运行状态，执行 `git fetch origin main`。
3. 记录本地 main 与 origin/main 的 SHA、任务分支和 worktree 路径。任务分支命名为 `codex/<任务名>`。
4. 在模块文档或 `docs/changes/` 中写明负责人及明确文件范围。同一文件存在并行任务时，先约定唯一写入负责人，再开始修改。
5. 若本地 main 含其他任务尚未推送的提交，记录其与 origin/main 的差异；本任务的发布不顺带推送这些提交。文档等独立任务可从 origin/main 建分支，完成远端主线整合后，再将该规则合回本地主线，保留原历史。

## 开发与同步记录

- 一个完整功能模块或业务切片完成后，集中执行覆盖受影响部分的验证，并同步模块记录。
- 记录功能模块迭代计数；纯文档/规则修改记为 0，不累计业务成功发布。
- 每完成 3 个功能模块，或者跨日继续任务时，刷新并整合主线；记录同步前 SHA、origin/main SHA、同步后 SHA 及迭代计数。
- 超过 48 小时仍未合并的任务，在交接文档用醒目的红色标记记录原因、未完成项和下一步，保留真实状态。

## 整合、推送与清理

1. 提交前审查差异，只暂存本任务的明确文件路径，核对没有环境文件、凭据和密钥。
2. 合并前再次 `git fetch origin main`，整合最新主线并完成必要的集中验证。
3. 使用普通 merge 整合本任务，再正常推送 main。推送被拒绝时重新获取、整合并验证，不强推。
4. 分别记录本任务提交、远端 main、共享本地 main 和实际运行版本；存在差异时说明来源，不把合并或推送当作业务上线。
5. 清理前确认本任务提交已进入目标主线、工作树干净，且无使用该工作树的运行任务。只删除本任务已合并的分支与 worktree，保留其他任务资源。

## 交接与验收口径

### 用户可见更新说明与默认发布

- **受管模型设置页及其专用 API 只返回模型显示名称和配置状态。** 不返回供应商、地址、协议、凭据引用、真实模型 ID 或官方参数来源；只读不能用禁用编辑表单代替。真实安装包门禁逐一打开四种配置的原生设置页并验证响应白名单；缺少设置页回执禁止发布。非受管自配连接保留既有编辑契约。
- **所有分发包的模型选择器只显示模型项，不显示供应商/协议抬头。** 这是产品呈现契约，不是本机配置清理。保留后台 provider 路由和凭据字段，不通过清空 `displayName`、改名、CSS 遮盖或合并路由伪造修复。原生选择器及 `/model` 共用规则；Bot、普通会话、群聊共用原生控件。
- 完整标准包构建必须执行 `verifyModelPickerDistribution`，使用实际打包 EXE 验证 fresh/两批旧测试配置 × Bot/普通会话/群聊，并验证选择后刷新仍保持；列表文本必须精确等于模型项，不以“模型个数正确/调用成功”替代标题检查。SDK 源码变更导致 hash/锚点不符时先更新扩展与验收，不跳过门禁。
- 已分发旧客户端的 backend-link v2/serviceUpdates=bundled 路径也必须真实验收：四配置×十二场景，旧链接服务先复现旧标题，再保留账号/home/端口/Cookie升级；活动服务目录的原生选择器hash必须等于本次包。runtime inventory 的每个 .naumi-original 扩展都必须进入 linked-service 原生同步事务，不能只比版本号。
- 发布前必须通过 `assertModelPickerRelease`：manifest 策略、实际原生 UI 文件 hash、真实 EXE 验收矩阵与本次安装器 SHA256 绑定。缺回执、旧回执或标题回归均阻止发布；手工发布同样先执行此门禁，不以手工 gh 命令绕过。
- 两个升级例必须先启动上一版真实EXE并打开模型列表，再用同一账号目录、浏览器缓存和端口启动新包验证。`NAUMI_PREVIOUS_EXE` 可指定固定上一版完整包，默认检查本机上一个patch版本的稳定交付目录；缺少旧包就补齐该输入，不把冷启动配置样本记成已验缓存升级。门禁比对实际原生目录返回的全部模型名，不绑定某三个别名或数量。

- 用户已明确要求：新版本在固定 main 构建、集中验收通过后默认发布到更新源，不停在本地包，也不为同一发布重复确认。用户明确要求本地包、暂不发布或冻结窗口时例外；发布不包含擅自安装或重启当前用户程序。
- `CHANGELOG.md`、Release 描述和 `latest.yml` 的 `releaseNotes` 面向终端用户，只写可感知的功能变化、体验改善和必要操作。不得把内部实施记录直接复制进去；供应商路由映射、凭据引用、内部字段、事务/迁移实现和测试环境等细节不写进用户更新说明。
- 产品说明应准确、中性，不把显示选项或配置声明写成未经验证的底层型号、能力或性能升级。技术依据继续留在对应模块实现记录。
- 发布前复核三处文案一致；仅修正文案时保持版本、安装包字节和校验值不变，分别回读 Release 与匿名更新清单。已打开的客户端窗口可能缓存旧说明，不通过打断下载或重启用户任务来刷新文案。

模块交接使用 [AGENTS.md 中的五项模板](../AGENTS.md#集中测试与开发记录)，并附任务负责人、明确文件范围、基线 SHA、同步记录与迭代计数。

- 验证命令必须配实际结果，标明属于静态内容、单元/集成、真实业务链路、Git 整合、构建或运行发布中的哪一层。
- 对涉及计费、权限、恢复、迁移的关键流程，记录成功、失败、重试、并发及恢复后的行为；未完成的验收继续保留。
- 新版本只从 main 的固定提交构建。功能发布仍需核对真实运行版本与用户可见结果。
- 纯文档变更检查内容、相对链接和 Git 差异即可；本规则更新不重建应用、不重启服务、不触发业务发布。
